# Flash-backed MODE parameter persistence for direct-access disks

**Experimental work in draft PR #13, not approved for flashing or merging.**

## Scope

This replaces the 0671S15-specific, SD-sidecar prototype with a generic
**hard-disk MODE SELECT/MODE SENSE** implementation. It is not restricted to
IBM, AS/400, any profile name, 520-byte disks or a particular SCSI target ID.
It applies to any instantiated fixed, removable, ZIP-style or MO direct-access
disk image on RP2040/RP2350 ZuluSCSI hardware with the reserved settings flash
region. Tape and CD-ROM behavior remains unchanged. Other MCU families without
the reserved region retain their existing MODE command handling.

It is **opt-in while under test**:

```ini
[SCSI]
PersistModePages = 1
```

The option is system-wide; there is no profile allowlist or block-size
allowlist. If an existing board has unfamiliar bytes in **any** settings-region sector
(even alongside a valid journal), the firmware refuses to overwrite them until the owner
explicitly opts in to initializing that reserved region:

```ini
[SCSI]
PersistModeFlashInitialize = 1
```

**Do not enable the initialization setting on physical hardware before
reviewing the exact flash contents and authorizing erase.** It is not needed
on completely erased settings sectors. After a valid journal exists, it should
be removed. Neither setting is turned on by this code change.

## Storage design

RP2MCU mapped external flash (unchanged):

| Offset | Size | Owner |
|---:|---:|---|
| 0 | 1,183,744 | bootloader/firmware |
| 1,183,744 | 16,384 | four-sector MODE-page journal in reserved settings area |
| 1,200,128 | 73,728 | immutable ZPDB |
| 1,273,856 | remainder | ROM drive |

Four **4 KiB flash erase sectors** act as a rotating journal. Each host
MODE SELECT with SP=1 and an actual change to saved parameters writes a
snapshot of **all disks' saved mode-page values** to the next sector. A
snapshot contains version, sequence, length, CRC32 of payload, CRC32 of header,
and compact entries (64-bit disk identity, page number, data length, page
bytes). The previous valid sector stays untouched until the new one is
erased, programmed, read back and validated. The largest saved-page snapshot
payload is 3584 bytes. If it would exceed available space, the command fails
rather than silently saving a partial set. Pages can be up to 255 data bytes,
with no arbitrary model/target/page-count allowlist. Journal metadata and
CRC validation exclude invalid/truncated records on startup; the newest valid
sequence wins, including sequence wraparound.

Every boot or device rescan loads the latest valid saved snapshot and clones
it into volatile CURRENT state. MODE SELECT with SP=0 updates CURRENT only;
SP=1 updates CURRENT and only the explicitly supplied SAVED pages. Reads
never rewrite flash. Flash is not written for repeated identical SP=1 saves.

Flash operations reuse the platform's existing
`platform_flash_read/erase/program` paths, including core1 mutex handling and
disabled interrupts around erase/program. It is **not** yet proven that the
latency of a flash sector erase is acceptable in the B10 command-completion
window. Real hardware timing needs validation.

No SD-card sidecar is written. Copying an image to another SD card attached
to the *same* ZuluSCSI board keeps its saved parameters if identity and
geometry match. Copying the SD card to **another ZuluSCSI board** does not
copy its flash journal. Flash ownership is device-local.

## Identity

A 64-bit FNV-1a key is derived from configured vendor, product, serial, bound
ZPDB profile name (if any), backing-image filename, and logical block size /
sector count. The SCSI bus ID is **not** part of the key when a filename can be
resolved; dynamic SCA ID changes can retain the same state. If no filename is
available, target ID becomes a fallback identity. A duplicate active key is
rejected to avoid two different disks sharing saved state.

Identity is derived from disk configuration, **not VPD write requests**. This
feature never changes INQUIRY/VPD data. Replacing or renaming an image, changing
the configured serial/profile, or changing its size intentionally isolates
the previous saved state.

## SCSI command semantics

- MODE SENSE(6)/(10) PC=0 CURRENT: overlay stored per-page bytes.
- PC=1 CHANGEABLE: report accepted page data as changeable, except format
  device page block-length bytes; no claim of vendor-specific *operational*
  side effects beyond readback.
- PC=2 DEFAULT: return the unmodified baseline generated by the existing
  MODE SENSE code or immutable ZPDB capture.
- PC=3 SAVED: overlay the flash-restored saved page bytes.
- MODE SELECT(6)/(10) PF=1, SP=0 changes only current; SP=1 also saves.
  PF=0 SCSI-1 vendor-format commands retain the legacy handler.
  The complete multi-page list is validated and staged before any commit.
- Short MODE SELECT pages such as the real 9404-B10
  `15 11 00 00 16 00` request are accepted when their data fits the
  corresponding, potentially longer, existing MODE SENSE page.
- Unsupported/duplicate/malformed pages and a request to alter sector
  length fail without changing any state. Snapshot capacity exhaustion,
  unavailable/foreign flash after persistence is requested, or a flash
  write/readback failure returns CHECK CONDITION rather than falsely
  acknowledging a successful save.
- MODE page code and subpage must be supported by the existing baseline.
  The firmware's existing MODE SENSE implementation does not expose
  subpages, so SPF/subpages are not newly invented by the persistence layer.

Preserving disk images requires a semantic guard: mode-selected 520/512/other
sector-length changes are rejected rather than silently reinterpreting
existing image bytes. These are the only intentional restrictions, not a
drive-type or model whitelist.

The existing MODE SENSE response-generation logic is authoritative for page
availability and immutable defaults; all flash state is a separate overlay.
No ZPDB record, captured identity, drive serial override, ROM drive, or
backing disk image is modified by the flash-mode feature.

## Host-side verification

```sh
python3 utils/test_as400_mode_select_length.py
python3 utils/test_mode_page_store.py
python3 utils/test_e11_tapes.py
```

The generic test host-compiles **the real MODE-page model and snapshot codec**
and tests the captured B10 22-byte command, generic 512-byte disk profiles,
6/10-byte selectors, multi-disk separation, PC=0/1/2/3, SP=0 vs SP=1, partial
page saves, changed image geometry rejection, multiple simultaneous saved
pages, flash journal recovery from torn/corrupt records, CRC/version checks,
sequence wraparound, and flash capacity exhaustion.

CI builds the available PlatformIO targets. Host tests do not replace hardware
flash fault-injection, on-target RP2040/RP2350 timing measurements, or a genuine
B10 power-cycle and IPL experiment.

## Non-destructive B10 validation

1. Preserve the known-good firmware UF2, current INI, profile store, full SD
   images, and SHA256 hashes before touching hardware.
2. Inspect the four reserved flash sectors for unknown content. In particular,
   do **not** turn on `PersistModeFlashInitialize` without confirming the
   region does not hold data from another firmware.
3. Flash an explicitly approved *test* build only after that inspection.
   Start with an expendable SD card / disk images; retain the real original
   images unmodified and offline.
4. Connect ZuluSCSI to a SCSI test host (not the physical B10). Save MODE
   pages for two different hard-disk models and two SCSI IDs. Repeat
   MODE SENSE PC=0/1/2/3 after reset and full ZuluSCSI power-off/on.
5. Inject simulated interrupted/CRC-invalid snapshots in the host unit test;
   power-cycle fault-injection on hardware should use a test board only.
6. Measure worst-case FLASH erase+program command timing under SCSI traffic,
   then perform a controlled B10 test with disposable copies and full traces.
7. Compare errors and SRC sequences against the unmodified firmware. Missing
   MODE persistence remains an **unproven** cause of `B601 0430`: the V3R1
   images successfully IPLed on the physical B10 before the Solstice D02
   round trip and later LIC/MULIC restoration.

No approval to flash hardware, alter original images or merge production
branches has been inferred from this development request.
